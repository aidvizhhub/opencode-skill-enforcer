# Внутреннее устройство

Один файл кода — `index.ts` в корне проекта.

## Карта функций

```text
readOptions                 разбор опций
expandHome                  "~/x" → домашний каталог
withoutPaths                выкинуть ссылки и пути из текста
stemWords                   токены для поиска (стемминг, стоп-слова)
labelOf                     подпись куска (заголовок)
atomsOf / splitDoc          файл → абзацы → блоки по размеру
clipBlock                   обрезка куска по границе абзаца
picksFromHits               попадания → куски (окно, склейка, отсев битых индексов)
selectBlocks                словесный поиск (IDF)
unitPreview                 короткое превью абзаца для показа модели
llmBroker                   семантический добор (скиллы + абзацы одним вызовом)
renderRule                  текст правила для system
setup                       карты сессии, touch, docUnitsFor, хуки
```

## Скиллы

Добор по смыслу: секция «Загружай, когда:» и ID весят 2, остальное описание — 1,
и всё домножается на вес редкости слова. Отбор трёхфакторный: абсолютный пол,
доля от лучшего в ходе и число совпавших слов (см. «Отбор скиллов» в `options.md`).
База (`alwaysSkills`) цепляется один раз за сессию: если скилл уже в контакте,
повторно не грузим.

Слова и у промпта, и у описания идут через один `stemWords` с грубым стеммингом
(от 6 букв берём первые 5). Без этого падежи не сходятся: на «расскажи про сабагента»
скилл про сабагентов не попадал. Ссылки и пути вырезаются до разбора — иначе имя
каталога `opencode-skill-enforcer` цепляло скилл про сам opencode.

### Брокер

Когда словесного отбора не хватает (скиллов меньше `minSkills` или у справочника не
нашлось ни одного блока), плагин делает **один** вызов модели на оба источника сразу
(`skillLlm` / `docLlm`). Модель отвечает двумя строками: `SKILLS: ...` и `DOCS: D<док>.<абзац>`.
Кандидатов-абзацев дают до `docLlmMax`, кандидатов-скиллов — только тех, что ещё не в
контексте и у кого есть словесное совпадение с запросом (до `skillLlmMax`): из полного
каталога в 40+ скиллов модель выбирает заметно хуже, чем из короткого списка. Запрос
идёт через `ctx.session.generate`, модель берётся из сессии. Если словесный отбор
справился сам — вызова нет. Время вызова пишется в лог строкой `broker: ... <мс>`.

**Когда модель не зовётся.** Вызов стоит 5–35 секунд, поэтому включается только там,
где выбирать есть из чего и есть смысл выбирать:

- скиллов не хватает, а лучших по числу совпадений кандидатов не больше, чем нужно —
  цепляем всех и идём дальше (`lexical enough`);
- по справочнику словесный поиск пуст, но пересечения есть и блоков не больше, чем
  нужно — берём лучшие (`doc lexical enough`);
- в справочнике нет ни одного слова из запроса — модель всё равно ответит `NONE`,
  поэтому не зовём её вовсе (`doc no overlap`).

Без последнего правила модель получала 33 блока документа, ни один из которых не
пересекался со словами запроса. На живых прогонах это стоило 20–34 секунды и
`NONE` в ответ.

На наборе из 16 типовых промптов доля вызовов модели упала с 75% до 44%, лексика
закрывает остальное.

Перед вызовом плагин смотрит в файловый кэш: ключ — нормализованный текст запроса,
значение — скиллы и хэши текста кусков справочников (не номера абзацев: при правке
файла номер сдвинется, хэш останется). Попадание в кэш закрывает и вызов модели, и
подстановку — в лог падает `broker: cache hit [...]`. Пустой ответ модели не затирает
прошлую удачную запись.

Правило в system каждый шаг сообщает: что за база в контакте, сколько рабочих загружено
в текущем ходу, что уже читается.

## Справочники

Файл режется на **блоки по размеру**: абзацы копятся, пока блок не станет весомым
(цель 600–1200 символов). Новый блок начинается у заголовка, если минимум уже набран.
Пустая строка внутри кода (fenced ` ``` ` или `~~~`) и между пунктами одного списка
кусок не рвёт. Заголовок отдельной строкой приклеивается к следующему абзацу.

Так AGENTS.md превращается в ~16 нормальных кусков вместо сотни огрызков по 60 символов.

Поиск идёт по телу текста: стемминг (слова от 6 букв → первые 5, короткие латинские
`mcp`/`api` целиком) плюс вес редкости (IDF). Порог — `minDocScore`, но не выше
числа значимых слов в запросе: в промпте из трёх слов в лучшем блоке совпадёт
максимум три, и жёсткий порог дал бы ложный ноль. Попадание раздувается на
соседние абзацы (`docWindow`), соседние окна склеиваются, обрезка — по границе
абзаца.

У каждого куска в подписи короткий хэш текста. Секцию правишь — хэш меняется, и кусок
приезжает заново; текст тот же — не дублируется.

Вставка помечается в тексте сообщения:

```text
<!-- skill-enforcer:doc-context -->
[AGENTS — «Название раздела» #1cplcqp]
…текст…
```

Перед вставкой плагин читает последние сообщения сессии и решает по факту: скилл и кусок
справочника, которые уже в контексте, повторно не подкладываются; если выпали (например,
после сжатия истории) — вернутся. Разобранные файлы кэшируются по `mtime`.

`docLlm: true` включает семантический добор (см. «Брокер»): когда словесный поиск не
дал ничего, модель выбирает абзацы вместе со скиллами — одним вызовом на оба источника.

## Состояние

Всё держится в памяти, ключи по `sessionID`:

```text
inContact       что уже в контакте (база + рабочие)
turnTask        рабочие скиллы, попавшие в контекст в текущем ходу
docCache        путь → разобранные абзацы (кэш по mtime)
injectedDocs    куски, подставленные в этой сессии (фолбэк, когда история недоступна)
seenAt          когда сессию видели в последний раз
```

Карты по `sessionID` подрезаются: сессия, к которой не возвращались сутки, забывается
(иначе сервис, который не перезапускают неделями, держит их все). `docCache` не чистится —
он keyed по пути и растёт только вместе с числом настроенных `documents`.

Выбор брокера ещё лежит в файле `cacheFile` — он переживает перезапуск плагина, но
не перезагрузку машины, потому что лежит в `/tmp`.

Вставленный текст живёт в истории сессии, поэтому `/new` (новая сессия) начинает с
чистого листа.
